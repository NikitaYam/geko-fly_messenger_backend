## Корректность и безопасность

### 🔴 A1. Статус «прочитано» в группе с удалённым участником никогда не наступит
**Где:** `MessageStatusService.minWatermarks()`, `WebSocketEventListener.broadcastPresence()`, `MessageStatusService.unreadCount()`.
**Суть:** после R10 удалённый пользователь остаётся «тумбстоуном» — строкой в `users`
и **участником своих чатов** (`chat_participants` не чистится). Расчёт статуса берёт
минимальную вотермарку по ВСЕМ получателям, включая тумбстоуна. Его вотермарка навсегда
`0` (он никогда ничего не прочитает).
**Чем грозит:** в групповом чате, где есть хоть один удалённый участник, все сообщения
у отправителя навсегда застревают в статусе `SENT` — галочки «доставлено/прочитано» не
появятся никогда. Аналогично `unreadCount` может считать «непрочитанным» для тумбстоуна
(в счётчик чужих чатов не попадает, но логика хрупкая).
**Как чинить:** исключать `deleted = true` пользователей из списка получателей в
`minWatermarks`, из co-participant-рассылки presence и из подсчётов. Технически —
добавить фильтр `AND p.user.deleted = false` в соответствующие выборки участников.

### 🟠 A2. `avatarUrl` и `attachment.fileUrl` принимаются как произвольные строки
**Где:** `UserService.updateProfile` (avatarUrl), `ChatMembershipService.updateChat`
(avatarUrl группы), `MessageService.saveMessage` (attachments[].fileUrl).
**Суть:** сервер сохраняет любую строку, что пришла от клиента, без проверки, что это
реальный путь к загруженному через наш upload файлу. Клиент может прислать
`avatarUrl = "/api/uploads/avatars/<чужой-файл>.png"`, внешний `https://…`, или мусор.
`stored_name` для вложения извлекается из этого URL как «последний сегмент» — им потом
оперирует relay/sweep.
**Чем грозит:** (1) можно подставить чужой аватар/файл по пути; (2) внешний URL в
avatarUrl → клиент сходит на чужой сервер (утечка факта онлайна, трекинг); (3) битый
`fileUrl` → неверный `stored_name`, relay не найдёт файл, «фантомные» вложения.
**Как чинить:** валидировать, что `avatarUrl` соответствует шаблону
`/api/uploads/avatars/{uuid}.{ext}`, а `fileUrl` — `/api/files/{uuid}.{ext}`; лучше —
принимать от клиента не URL, а `storedName`/идентификатор загрузки, а URL строить на сервере.

### 🟠 A3. Нет ограничения частоты на отправку сообщений и загрузку файлов
**Где:** `MessagesController`, `FileController` — rate-limit есть только на логине (R2).
**Суть:** авторизованный пользователь может слать тысячи сообщений/запросов в секунду.
**Чем грозит:** один аккаунт способен засыпать WebSocket-рассылку, раздуть БД, забить
диск загрузками (до срабатывания резерва 512 МБ). Для 50 друзей маловероятно, но дыра есть.
**Как чинить:** лёгкий per-user лимит (тот же приём, что `LoginAttemptService`), либо
ограничение на nginx.

### 🟠 A4. Wildcard-инъекция в поиске пользователей
**Где:** `UserRepository.searchByLoginOrName` — `LIKE CONCAT('%', :q, '%')`.
**Суть:** это НЕ SQL-инъекция (параметр экранирован), но спецсимволы LIKE (`%`, `_`) в
запросе не экранируются. `query=%` вернёт всех, `query=_` — тоже широкое совпадение.
**Чем грозит:** обход «минимум 2 символа», перечисление всех пользователей одной строкой.
Для закрытого приложения это осознанно приемлемо (см. решение по R8), но стоит знать.
**Как чинить:** экранировать `%` и `_` во входной строке перед подстановкой в LIKE.

### 🟠 A5. Presence на отключении: гонка «последней сессии»
**Где:** `WebSocketEventListener.handleSessionDisconnect` → `presenceService.isOnline`.
**Суть:** при отключении сессии Spring и наш слушатель обновляют `SimpUserRegistry`
несогласованно по времени. `isOnline` может ещё видеть закрывающуюся сессию → событие
«офлайн» не отправится.
**Чем грозит:** иногда «зелёная точка» у собеседника гаснет не сразу (до следующего
действия). Присутствие best-effort, данные в БД не пишутся — не критично.
**Как чинить:** отправлять офлайн отложенно (через n секунд перепроверить `isOnline`),
либо смириться (осознанный best-effort для 50 человек).

### 🟡 A6. Push кладёт текст сообщения в data-payload
**Где:** `MessageService.broadcastMessage` → `pushService.pushToUser(..., "body", content)`.
**Суть:** превью сообщения уходит в FCM и показывается на заблокированном экране.
**Чем грозит:** приватная переписка видна на локскрине; текст проходит через серверы Google.
**Как чинить:** учесть будущую настройку «скрывать текст в уведомлениях» — слать
обезличенное «Новое сообщение», а текст подтягивать в приложении после разблокировки.

### 🟡 A7. CORS открыт для всех источников
**Где:** `WebConfig` — `allowedOrigins("*")`.
**Суть:** осталось с этапа разработки. Токен-авторизация (не куки) снижает риск, но
на прод стоит сузить до реальных доменов клиента/PWA.

### 🟡 A8. Нет ограничения размера группы
**Где:** `ChatMembershipService.addParticipant`.
**Суть:** ADMIN чата может добавлять участников без предела; каждое действие плодит
WS-рассылку по всем участникам.
**Как чинить:** мягкий лимит участников (например, 200) и/или на число чатов.

### 🟡 A9. Тумбстоун-участник виден в списке участников группы навсегда
**Где:** `ChatService.getParticipants` возвращает и удалённых (deleted) пользователей.
**Суть:** «Удалённый пользователь» остаётся в списке участников группы. Это следствие
дизайна R10 (история цела ценой вечного тумбстоуна). Обычно приемлемо, но стоит хотя бы
не показывать его онлайн-статус и, возможно, помечать отдельно.

## Производительность

### 🟠 P1. N+1 запросов в списке чатов
**Где:** `ChatService.getChats` → `buildChatResponse` на каждый чат.
**Суть:** для каждого чата отдельно выполняются: «последнее сообщение» (1), «другой
участник» → `findByChat` (1), `unreadCount` → `findByChatAndUser` + `countUnread` (2).
Итого ~4 запроса × число чатов пользователя.
**Чем грозит:** при десятках чатов — десятки-сотни мелких запросов на один экран списка.
Для 50 человек терпимо, но это классический N+1.
**Как чинить:** агрегирующие запросы (одним JPQL собрать последние сообщения и счётчики
непрочитанного по всем чатам пользователя), либо кэш последних сообщений.

### 🟠 P2. `@ManyToOne` по умолчанию EAGER
**Где:** `MessageEntity.chat/sender`, `AttachmentEntity.message`, `ChatParticipantEntity.chat/user`.
**Суть:** у `@ManyToOne` fetch по умолчанию EAGER. При загрузке страницы сообщений
Hibernate дополнительно тянет чат и отправителя каждого сообщения (частично покрывается
кэшем сессии, но всё равно лишние выборки).
**Как чинить:** проставить `fetch = FetchType.LAZY` там, где связь не всегда нужна, и
подгружать через `JOIN FETCH` по необходимости.

### 🟡 P3. `markDeliveredUpToLatest` пишет в БД на каждый просмотр истории
**Где:** `MessageService.getMessages` (стало `@Transactional`, не readOnly).
**Суть:** каждый `GET .../messages` двигает вотермарку delivered и (при изменении) шлёт
WS-событие. Есть guard «только если вотермарка меньше нового», так что запись происходит
не всегда — но GET перестал быть чисто читающим.
**Чем грозит:** write-амплификация и WS-трафик при активной прокрутке. Терпимо, но GET
с побочным эффектом — не самый чистый контракт.
**Как чинить:** выделить пометку доставки в отдельный вызов/событие от клиента, а GET
оставить readOnly.

### 🟡 P4. Sweep грузит все живые вложения раз в час и считает по каждому
**Где:** `StorageSweepService.purgeDeliveredAndExpired`.
**Суть:** `findByFileDeletedFalse()` + на каждое вложение `findByChat` (участники) и
`countByAttachment`. N+1 внутри планового прохода.
**Чем грозит:** при накоплении файлов проход дорожает. Раз в час — не горит.
**Как чинить:** выбирать кандидатов сразу запросом (например, вложения, у которых число
доставок = числу получателей, или старше срока), а не перебирать все.

### 🟡 P5. Рассылка событий — цикл `toUser` по каждому участнику
**Где:** `EventPublisher.toUsers`, `ChatMembershipService`, `MessageStatusService.notifyOthers`.
**Суть:** отдельная отправка каждому участнику. Для больших групп — много мелких сообщений.
**Как чинить:** там, где payload одинаков, использовать топик `/topic/chat/{uuid}` с одной
публикацией вместо N адресных (но тогда нужна подписка/отписка по членству). Для 50 человек
текущий вариант проще и достаточен.

## Что уже сделано хорошо (чтобы не «чинить» лишнего)
- Единый `UserMapper`, `EventPublisher`, `FileTypeRules`, `StorageProperties` — одна точка правды.
- Тонкие контроллеры, вся логика в сервисах.
- Все временные метки — `Instant`/`timestamptz` (UTC), нет наивных дат.
- Мягкое удаление сообщений и анонимизация пользователя сохраняют историю.
- FCM корректно отключается без ключа — dev/прод без Firebase не падают.
- Проверки доступа (`checkAccess`, `requireChatAdmin`) на всех чувствительных операциях.
